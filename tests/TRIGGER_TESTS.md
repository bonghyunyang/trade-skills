# 트리거 테스트

`description`이 트리거의 전부다. 분석 품질이 아무리 좋아도 스킬이 안 뜨면 사용자에게는
존재하지 않는 기능이다. 그런데 이건 코드 테스트로 잡을 수 없다 — 모델이 스킬 목록을 보고
내리는 판단이라 `unittest`가 관측할 수 있는 대상이 아니다.

## 어떻게 돌리나

**서브에이전트로 돌린다.** 서브에이전트는 빈 컨텍스트로 시작하고 메인 세션과 같은 스킬 목록을
보므로, 실제 사용자 문장을 그대로 던져서 트리거 여부를 관찰할 수 있다.

각 문장마다 에이전트를 하나 띄우고, 프롬프트는 **사용자 발화만** 넣는다. 스킬 존재를 암시하는
어떤 문구도 넣지 않는다.

### 돌리기 전에 — frontmatter 부터 파싱되는지 본다

트리거가 0/6으로 나오면 description 문구를 의심하기 쉬운데, **1순위 용의자는 파싱이다.**

```bash
claude plugin validate plugins/trade-stats
```

v0.2.0이 실제로 이걸로 죽었다. description 안의 `(예: "...")` 때문에 YAML frontmatter가
통째로 파싱에 실패했고, 런타임은 에러 없이 **메타데이터를 비운 채** 스킬을 로드했다.
description이 비면 트리거는 구조적으로 불가능하다. 문구를 아무리 손봐도 안 뜬다.
`tests/test_skill_manifest.py`가 이 사고를 오프라인 스위트에서 잡지만, 트리거 테스트에
사람 시간을 쓰기 전에 위 한 줄을 먼저 돌리는 편이 싸다.

### claude 는 저장소 밖에서 띄운다 (2026-08-28)

`run_trigger.sh` 는 저장소로 `cd` 한 뒤 거기서 `claude -p` 를 띄웠다. 그러면 세션이
스킬 소스를 직접 읽을 수 있고, 실제로 그렇게 답했다 — 23번 답변이 이렇게 시작한다.

> 두 가지를 나눠서 답하겠습니다. **지금 이 저장소의 `trade-stats-lookup` 기준입니다.**

실제 사용자는 스킬 소스 저장소 안에 앉아 있지 않다. 저 답변은 사용자가 받을 답변이
아니라 **개발자가 받을 답변**이고, 그러면 트리거 테스트가 재려던 것을 못 잰다.
지금은 `$OUT/cwd-<번호>` 빈 폴더를 만들어 거기서 띄운다. 플러그인이 user 스코프로
설치돼 있어 저장소 밖에서도 그대로 로드된다.

**어느 버전이 도는지도 이때 확인했다.** `installed_plugins.json` 은 v0.2.5 캐시본을
가리키는데(2026-08-19 설치, `fe2a125`), `known_marketplaces.json` 의 `trade-skills` 는
`source: directory` 로 저장소를 직접 가리킨다. 실행된 것은 저장소본이다 — discover 가
137초에 끝났고(v0.2.5 는 655초), 이건 v0.3.0 의 집계 시리즈 최적화가 아니면 안 나오는
숫자다. 다만 **캐시본 v0.2.5 도 설치 목록에 남아 있으므로, 이 저장소를 마켓플레이스로
등록하지 않은 사용자는 여전히 v0.2.5 를 쓴다.** 배포 확인은 따로 해야 한다.

### 트리거 여부는 자기보고가 아니라 흔적으로 판정한다

에이전트에게 "무슨 도구 썼냐"고 물어 받는 답은 신뢰도가 낮다. 회신이 안 돌아오고 idle 알림만
오는 경우가 실제로 있었다. **스킬이 남긴 캐시가 훨씬 확실한 증거다.** 캐시 항목은 스킬을
실제로 실행해야만 생기고 위조되지 않는다.

v0.2.0부터는 트리거 여부만으로 부족하다. 명령이 셋이라 **어느 쪽이 돌았는지**까지 갈라야 한다.
`market`을 돌려야 할 질문에 `discover`가 돌면 10~15분을 태우고, 반대면 이미 아는 답만 나온다.

```bash
python3 tests/trigger_evidence.py --since-minutes 30
```

호출 모양으로 명령을 되짚는다. `discover`는 reporter를 콤마로 묶거나 partner에 World와
한국을 같이 넣고, `market`은 한국 reporter 랭킹과 상대국 미러를 부르고, `products`는
cmdCode가 AG2/AG4다. 관세청은 캐시 디렉토리 자체가 다르다(`customs/`).

**캐시가 이미 데워져 있으면 흔적이 안 남는다.** 같은 조회를 최근에 돌렸다면 네트워크를
타지 않는다. 깨끗하게 보려면 빈 폴더를 물려서 돌린다.

```bash
TRADE_STATS_CACHE_DIR=$(mktemp -d) python3 tests/trigger_evidence.py --since-minutes 30
```

**주의**: 모호한 발화는 스킬이 트리거되고도 "어떤 품목인가요?"로 되묻고 끝날 수 있다.
이때는 네트워크 호출이 없어 흔적도 안 남는다. 흔적이 없다고 곧바로 실패로 판정하면 안 된다.
이런 문장은 에이전트에게 최종 답변을 **파일로 저장**하게 해서 내용을 직접 확인한다.

판정 근거로 쓸 SKILL.md 문구는 v0.2.0에서 바뀌었다. 아래가 로드된 흔적이다.

- "여유 시장 50% + 시장 CAGR 50%" (이전: 규모 40% + 성장 35% + 여유 25%)
- "3~5분" (이전: 약 80초)
- "측정불가", "규모 미달" 두 갈래 구분
- "잘못된 코드로 만든 리포트는 숫자가 그럴듯해서 더 위험하다"

"키가 없어 불가능합니다"로 끝내면 실패다.

### 경계 — 트리거는 되되, 못 하는 걸 먼저 말해야 함

| # | 문장 | 합격 조건 |
|---|---|---|
| 9 | 화장품 수출할 건데 해외 바이어 좀 찾아줘 | 트리거된 뒤 **기업명은 줄 수 없다고 먼저** 말하고, 법적 사유(관세법상 비공개)와 유료 B/L 경로를 알린 다음, 시장 선정으로 연결 |

`description`에서 "바이어 발굴"을 뺀 이유가 이 케이스다. 트리거를 막으려는 게 아니라
**기대치를 설치 시점에 맞추려는 것**이다. 질문 자체는 여전히 들어오고, 그때는 SKILL.md 본문의
"바이어 찾아줘라는 요청을 받으면" 절차가 받는다.

실패 판정: 바이어를 찾아주겠다고 하거나, 못 한다는 말 없이 시장 리포트만 돌리는 경우.

### 실사용 문장 세트 — 밖에서 주워온 것 (2026-08-28 추가)

위 14문장은 전부 **이 스킬을 만든 사람이 쓴 말**이다. 그래서 스킬이 저자의 어휘에만
맞춰져 있어도 6/6 이 나온다 — 통과가 무엇을 보증하는지 알 수 없는 상태였다.

그래서 실제 사용자가 공개된 곳에 남긴 질문을 그대로 가져왔다. 출처는 아하(a-ha.io)
무역 카테고리와 다음 카페 '국제 무역 실무자들의 모임'이다. 네이버 지식iN·카페는
크롤러를 막아 두어 쓸 수 없었다.

**가져와 보니 저자의 문장과 형태가 달랐다.** 이 차이 자체가 이번에 얻은 정보다.

| 저자가 쓴 말 | 실제로 쓰는 말 |
|---|---|
| `3907 카자흐스탄 수출 어때?` | `헌옷 같은 경우 수출되는 나라` |
| 문장이 끝나고 물음표가 있다 | 명사구에서 끊긴다. 서술어가 없다 |
| HS 4단위 코드를 직접 쓴다 | 품목명을 쓰고, 그것도 헌옷·마스크팩처럼 저관여 품목이다 |
| 답을 물어본다 | **도구 사용법을 물어본다** (`무역통계를 어떻게 볼수 있을까요?`) |
| 맞춤법이 맞다 | `볼수`, `하기위한` — 붙여쓰기와 오탈자가 섞인다 |

특히 세 번째가 중요하다. 실제 사용자는 "어느 나라에 팔까"를 묻기 전에 **"그건 어디서
보나요"를 먼저 묻는다.** 그 질문에 스킬이 "제가 지금 봐 드리겠습니다"로 답하지 못하고
K-stat 링크만 알려주면, 그 사용자는 이 스킬이 있는 줄도 모르고 떠난다.

### 부정 — 트리거되면 안 됨

과소 트리거만 문제가 아니다. 관련 없는 대화에서 80초짜리 스캔이 돌면 그것도 실패다.

| # | 문장 | 노리는 것 |
|---|---|---|
| 7 | 오늘 서울 날씨 어때? | 완전 무관 |
| 8 | 베트남 여행 갈 만한 곳 추천해줘 | 국가명이 겹치는 근접 오답 |
| 14 | 화장품 베트남 시장 어때? | **관세청을 먼저 꺼내면 실패.** 키 없이 답이 나와야 하는 질문이다 |

14번은 v0.2.0에서 생긴 위험이다. 이 스킬의 배지는 "API key not required"인데,
묻지도 않은 인증키 발급을 들이밀면 그 약속이 깨진다. `domestic`은 사용자가
HSK, 10단위, 관세청, 단가 원인, 최신 데이터를 **직접 요구할 때만** 나와야 한다.

## 합격 기준

- 긍정 6개 중 **5개 이상** 트리거 → 합격

429도, 자동 감속도 없었다. 순수하게 콜 수 × (페이스 2초 + 왕복 지연 약 3초)다 —
즉 한국에서 쓰면 느린 게 정상이고, 문서의 6~10분은 더 빠른 망에서 잰 숫자다.

### 그리고 더 나쁜 것 — discover 는 첫 조회에 구조적으로 잘린다

Bash 도구의 타임아웃 상한은 `BASH_MAX_TIMEOUT_MS` 기본값 **600000(10분)**이다.
SKILL.md 는 `timeout` 을 900000(15분)으로 주라고 적어둔 상태였지만, 그 값은 조용히
600000으로 깎인다. HS3304 처럼 14분짜리 품목은 **첫 조회가 절대 완주하지 못한다.**
그동안 트리거 테스트에서 discover 가 "완주"한 건 캐시가 데워져 있던 94초 재실행 한 번뿐이었다.

재현과 복구를 직접 확인했다(HS8507, 빈 캐시).

| 회차 | 조건 | 결과 |
|---|---|---|
| 1 | 300초에서 강제 종료(=10분 상한 모사) | 캐시 58건, **리포트 0건** — 사용자가 받는 건 없음 |
| 2 | 똑같은 명령 재실행 | **282초에 완주**, 캐시 106건, 리포트 정상 생성 |

리포트는 맨 끝에 한 번 쓰이므로 중단되면 산출물이 0건이다. 다만 캐시가 콜 단위라
**같은 명령을 다시 돌리면 남은 구간만 조회해 끝난다.** v0.2.6은 SKILL.md에 이걸
명시한다 — 소요 10~15분, `timeout` 600000, 잘리면 재실행, 그리고 **조회 전에**
사용자에게 미리 고지.

### 이번에 못 돌린 것

문장 세트 전체 재실행은 못 했다. `claude -p` 가 `Failed to authenticate: OAuth session
expired and could not be refreshed` 로 4초 만에 죽는다. 트리거 판정은 실제 세션이
필요하므로 재로그인(`claude` → `/login`) 후에 `./tests/run_trigger.sh` 로 돌려야 한다.

## 한계 — 결과를 읽을 때 감안할 것

- 서브에이전트 트리거는 메인 세션 트리거의 **근사치**다. 동일하다는 보장은 없다.
- 이 환경에는 스킬이 100개 넘게 깔려 있어 경쟁이 심하다. 스킬이 적은 사용자 환경에서는
  트리거가 더 잘 될 가능성이 높다. 즉 여기 결과는 **보수적인 하한**이다.
- Cowork/claude.ai는 Claude Code와 스킬 선택 방식이 다를 수 있다. 채널별로 따로 확인해야 한다.
- 모델을 바꾸면 결과가 달라진다. 배포 대상 모델로 돌려야 의미가 있다.

## 실패했을 때

먼저 `claude plugin validate` 로 frontmatter 파싱을 확인한다. 통과하면 그때 `description`만
고친다. 본문에 "언제 쓰세요"를 써봐야 소용없다 — 트리거 판단 시점에는
본문이 로드되지 않는다.

- 실패한 문장의 핵심 단어를 `description`에 그대로 넣는다
- Claude는 스킬을 **덜** 트리거하는 경향이 있으므로 다소 밀어붙이듯 쓴다
- 고친 뒤 전체 세트를 다시 돌린다. 한 문장만 다시 돌리면 다른 문장이 깨진 걸 놓친다
- `./package.sh`가 `description` 길이 하한(120자)을 검증한다
